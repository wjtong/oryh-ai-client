评审代码基线：`plugin-split` / `7c11b42`，相对 `main` / `031efcf`。文档落盘时分支为 `0aeb1f1`；该提交仅更正补丁历史说明，没有改变被评审代码。

## 结论与评审范围

同意重构方向，但不建议把当前分支直接认定为“插件化已经完成”。命令流、页面登记和领域包拆分改善了原有结构；合并前应收口命令流可靠性问题，业务验收则必须包含模型填写内容的正确性。

本次只读检查分支差异、[重构记录](14-dsh-plugin-migration.md)与本机 `/Users/wtong/git/deepseek-harness` 的公共接口。没有修改业务代码，没有运行会生成文件的构建，也没有重新回放浏览器流程。文档中的 188 项测试是重构阶段的已有记录，不是本次独立复跑的结果。以下区分静态代码发现、文档实测证据和待验证的设计建议。

## 应保留的设计

- 四个轮询合并为一个命令流，由业务视图共享会话命令状态。
- 页面登记表集中管理标识、入口规则和模型可见名称；客户端保留有类型约束的展示映射。
- 领域服务通过窄结构接口依赖连接、HTTP 和存储，避免反向依赖整个 core。
- 单元测试随领域迁移，贯穿真实连接、凭据和 HTTP 的集成测试保留在组合层。
- 模型填写建议与正式保存、提交、审批继续分离，传统 UI 和 Chat 共用业务操作与权限规则。

## 1. 合并前：修正命令流的通知丢失窗口

依据：[BusinessChat.commands](../packages/dsh-host/src/business-chat.ts)，评审基线第 191–207 行。静态代码发现，尚未新增测试复现。

当前生成器先 `yield` 一帧，然后才设置下一次等待的 `wake`。如果消费者正在处理上一帧，新命令此时触发 `changed()`，回调会因为 `wake` 为空而没有留下待处理通知。消费者随后请求下一帧时，生成器可能一直等到另一次变化，导致本次命令延迟或工具等待超时。

整集快照便于重连恢复，但不能自动消除这个窗口。建议使用递增版本或待发送标记保存变化，允许合并多次变化，但确保消费者最终能收到最新整集。取消和卸载也应覆盖相同窗口。

验收建议：

- 消费 baseline 后、请求下一帧前发布命令，下一帧仍能收到命令，无需后续变化唤醒。
- 消费者较慢、连续发布或撤销命令时，最终状态与 Host 当前快照一致。
- 在等待中及处理上一帧时取消，都能结束订阅并释放监听器。

## 2. 合并前：区分断线、业务拒绝和绑定失效

依据：[createCommandStream](../packages/web/src/client/remote.ts)，评审基线第 64–90 行；[CommandStream](../packages/web/src/client/command-stream.tsx)，第 58–76 行。

静态代码显示两种不一致的失败处理：

- 命令流把 baseline 前的任何异常都视为终态。首次连接短暂失败，或重连时网络尚未恢复，也可能永久停止联动。
- 建立绑定失败时每 500ms 重试，没有区分暂时失败与不可恢复的身份冲突。

建议按错误类别统一连接状态：连接中、已同步、重连中、被拒绝。网络故障采用可取消的退避重试；权限拒绝、身份冲突明确停止并显示恢复入口。终态不应继续把旧的待执行命令作为有效命令发布。

同时审查绑定所有权：清理请求目前只按 Session 标识处理。旧实例异步清理晚于新实例绑定完成时，应确保不会清掉新绑定。这是待验证的生命周期风险，不作为已复现缺陷；可考虑绑定代次或租约标识，也可以用其他机制证明顺序与所有权成立。

验收建议：

- 首帧前短暂断网、已连接后断网、服务重启后恢复，均能重新同步。
- 业务拒绝不会无限重试，用户能看到明确状态。
- 快速切换 Session、卸载再挂载、旧清理请求延迟到达，不影响新的有效绑定。
- 增加客户端流适配器测试，而不只验证 Host 能重新发送 baseline。

## 3. 业务验收前：把工时选错项目作为正确性缺陷处理

依据：[重构记录中的“第 5 步的基线回放”](14-dsh-plugin-migration.md)及 [TimesheetChat 工具回执](../packages/dsh-host/src/timesheet-chat.ts)，评审基线第 94–100 行。

已有文档记录四次回放中两次选错项目。样本不足以推断一般发生率，但足以说明这不是可以忽略的验收偏差。“错值来自模型工具参数”说明它未必由抽包引入，不能证明产品行为正确。

当前校验确认项目 ID 属于可用项目，不能证明它对应用户要求的项目。成功回执也没有返回页面实际生效的字段，模型容易按自己的意图复述结果。

建议：

- 工具回执从页面确认后的状态取得项目 ID、名称、日期、每日工时及合计，不能只回显原始工具参数。
- 项目解析与选择增加名称、ID 的一致性检查；重名或歧义时要求明确选择。
- 页面标出本次修改，核对环节直接展示实际项目和工时。
- 保留正式确认边界；填写成功不等于保存成功。

回传名称能帮助发现错误，但不能独立阻止选错项目。验收应分别测试名称解析、ID 映射、页面实际值和工具回执，并覆盖重名、先反问再填写、跨页后填写、用户纠正项目等场景。

这可以作为与结构重构独立的缺陷跟踪，但不能在未解决时把工时业务基线标成全部通过。

## 4. 下一阶段先决策：领域库还是独立业务插件

依据：[Host 组合入口](../packages/dsh-host/src/index.ts)，评审基线第 34–52 行，以及各领域包的 manifest。

当前领域包已拆开，但服务仍由一个 `dsh-host` 集中创建；页面组件和工具编排也主要集中在 Host、Web 中。这是有效的模块化，尚未实现各领域独立启用、停用和卸载。

不建议以包数量作为完成指标。先明确产品是否需要“某企业只启用库存、不启用工时”：

| 目标 | 建议 |
| --- | --- |
| 整体交付 ORYH 工作台，需要清晰维护边界 | 两个 Harness 插件加多个领域库可以成立，无需继续机械拆包 |
| 按企业组合业务模块，独立启停或升级 | 定义领域插件的服务、Remote、工具、页面注册及卸载契约 |

若选择独立插件路线，先规定禁用领域后如何撤销菜单、工具和页面上下文、取消命令等待、处理仍打开的页面，以及保留可恢复草稿。`dsh-connections`、`dsh-workbench` 的职责应先写清，再决定是否抽包。

页面登记表也应区分入口展示策略和业务操作授权，不能因为菜单隐藏就认为服务端数据访问已被限制。不要为未来可能的扩展提前引入过重的动态注册框架。

## 5. 构建与 Harness 复用：把限制变成可验证的契约

依据：[客户端流实现说明](../packages/web/src/client/remote.ts)、[补丁守卫](../scripts/check-dsh-patch.mjs)及 [补丁文件](../patches/deepseek-harness-external-remote.patch)。

### 核对公共流组件的实际可用性

“外部插件只能导入 Harness 类型、不能导入值”的说明过于宽泛。本机 Harness 的 `@deepseek-ai/dsh-api-gateway/client` 已公开导出 `RemoteSnapshotStream`；但公开导出本身也不足以证明当前外部 bundle 可以直接加载它。

建议在具体版本上核对模块加载、运行时导出和依赖注入约束，做最小集成验证。若确实无法复用，应记录准确限制、对应版本和恢复复用的条件，再保留尽量小的适配层；不要由这一处限制扩展出另一套通用连接框架。

### 补丁检查不能只依赖源码注释

当前守卫检查生成器源码里的标记，能发现部分漏补丁情况，但不能证明正在执行的生成器产物包含修复。建议固定 Harness 基线，验证补丁与基线匹配，并断言生成产物包含普通 Remote、流式 Remote 的预期描述符。

验收应包含从干净工作区按文档完成依赖准备、补丁应用、构建和 Profile 解析，避免只在已手工修复的本机工作区通过。补丁已有版本失配历史；本仓留存补丁改善了可恢复性，不代表与上游同步的风险已经消失。

## 建议顺序与暂缓项

1. 优先解决命令流通知、异常分类及绑定生命周期，并补相应测试。
2. 单独收口工时项目选择与实际回执，建立业务正确性验收。
3. 明确是否需要领域独立启停，再决定连接、工作台和领域插件边界。
4. 完善干净环境构建与 Harness 公共组件的集成验证。

agent preset、进一步增加包数量、合并两套加密存储实现，可以放在上述问题之后。它们有维护价值，但不应抢占联动可靠性和业务正确性的优先级。
