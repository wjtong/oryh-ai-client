# S0（P0）工作包验收标准

日期：2026-09-12。基线：`plugin-split` / `96b9f51`。

状态：建议稿。本文把 [多租户服务器版实施方案](19-multi-tenant-server-plan.md) 的 P0 收敛成可判定的验收条目，供 S0 工作包直接使用。它不改变那份方案的结论，只把"验证什么、怎样算过、什么情况下停"写死。

P0 的目的不是建设，而是**证伪**：在投入控制层、数据库和代理实现之前，先确认这套架构能不能在 Harness 现有公共能力上成立。因此每一条都必须有二元判据和明确的停止条件；"看起来能跑"不算通过。

## 顺序与并行

```
S0-0 可复现构建（门槛）
      │
      ├── S0-1 反向代理下的原生前端完整性   ← 最可能触发停止
      ├── S0-2 多身份隔离与资源底噪
      └── S0-3 ORYH 授权契约               ← 外部依赖，最早启动
```

- **S0-0 是门槛**，不是实验：构建不可复现时，其余三项的测量结果都不可信。
- **S0-3 最早启动**，因为它依赖 ORYH 侧配合，等待时间不由我们控制。
- **S0-1 优先于 S0-2 的路由子项**：伪造路由句柄的测试需要代理已经存在。S0-2 的隔离与资源测量不依赖它，可立即并行。
- 四项全部达标才进入 P1。任何一项触发停止条件，先回到架构决策，不得"带着已知缺口"推进。

## S0-0 可复现构建（门槛）

**为什么它排在最前。** 本仓依赖一个**尚未进入上游**的 typert 生成器补丁，而 DSH 仍是 prerelease。已知事实：该补丁在 `0.1.5-rc.1 → rc.2` 升级后已经失配，且长期无人发现——当时的守卫检查的是**生成器源码里的注释**，而生成器实际从构建产物运行，两者可以长期不一致。守卫已于 2026-09-12 改为检查执行中的产物（见 [迁移记录](14-dsh-plugin-migration.md)）。

在此之前，从未做过"全新克隆 + 全新安装"的冷启动验证。已验证的只是"清空构建产物后可重建"，两者不等价：依赖解析层面的问题测不到。

**步骤**

1. 在干净目录分别全新克隆 ORYH AI Client 与 Harness，锁定 Harness commit。
2. 严格按 README 顺序执行：装 Harness 依赖 → 应用补丁 → 构建 Harness → 装本仓依赖 → `verify` → `profile:install` → `start`。
3. 记录版本锁定清单：Harness commit、补丁 sha256、Node/pnpm 版本、生成描述符数量。
4. 重复构建一次，比对生成产物。

**成功判据（全部满足）**

| 判据 | 观测方式 |
| --- | --- |
| 全程只执行文档中的命令，无任何未记录的手工修补 | 操作记录逐条对照 README |
| `check-dsh-patch.mjs` 零错误且零警告 | 退出码 0，stderr 为空 |
| 生成描述符与基线一致 | `typert.remote-client.d.ts` 含 2 个流式、86 个普通 Remote |
| 两次构建产物一致 | `typert.remote-client.d.ts` 逐字相同 |
| 浏览器能进入工作台并拉到真实业务数据 | 人工确认一次业务列表 |

**停止条件**

- 需要任何未写进文档的手工步骤 → 先补文档，重跑本项。
- 补丁无法干净应用到锁定 commit → **先解决补丁的上游化或重导出，再继续**。这不是绕过项：产品化依赖一个会随上游漂移的补丁，必须有负责人和时间点。

**产出**：干净环境构建说明、版本锁定清单、（建议）一条每日 CI 冷启动任务。

## S0-1 反向代理下的原生前端完整性

**为什么它是 go/no-go。** 方案 §4.3 已写明"不能只让首页能够打开"。本次会话中观察到的几项事实说明它比清单看起来更难：boot manifest 在**服务启动时固化**（改了插件产物不重启服务器，浏览器仍拿到旧的）；插件 bundle 的 URL 由服务端生成；mux 固定在 `/api/remote.mux`；模块加载器按**裸包名**建键并对 `/client` 后缀做归一。路径前缀方案因此需要同时改写 HTML、boot manifest、插件 URL、WebSocket URL 与 Cookie 路径。

**步骤**

1. 以路径前缀 `/{handle}/` 反代**一个** runtime，逐项过下表。
2. 同样做子域方案 `{handle}.<域>`。
3. 同一 origin 下**同时**挂两个 runtime，验证 Cookie 不互相覆盖。
4. 每一项标注为：原生通过 / 仅需代理层改写 / 需改 Harness 私有实现。

**必须通过的面**

HTML 入口、boot manifest、插件 bundle、静态资源、CSS 与 sourcemap、`/api/*` REST、`/api/remote.mux` WebSocket、流式 Remote、文件下载、Cookie（路径与 SameSite）、前端深链刷新。

**成功判据（全部满足）**

| 判据 | 观测方式 |
| --- | --- |
| 上表每一项为"原生通过"或"仅需代理层改写" | 三分类清单，零项落在"需改 Harness 私有实现" |
| 任意深链直接刷新可用 | 至少覆盖会话页与业务页各一 |
| WebSocket 断开后能重连，流式输出中断后能恢复 | 主动断网再恢复 |
| 文件下载在前缀/子域下可用且带鉴权 | 下载一次会话日志 |
| 浏览器从不接触 runtime 内部端口或启动 token | 抓包与前端全文检索 |
| 两个 runtime 同挂一个 origin，Cookie 不互相覆盖 | 交替操作两个标签页 |

**停止条件**

- 任一必需面**只能**靠改 Harness 私有实现通过 → **不进入 P1**，转上游扩展点讨论。零散代理补丁不得进入生产。
- 仅子域方案可行：可接受，但必须把通配证书、host-only Cookie、DNS 记录写进部署前提，并重估运维成本与成本归属。

**产出**：接口暴露三分类清单、认证与代理选型 ADR、可复现的代理配置样例。

## S0-2 多身份隔离与资源底噪

**为什么两件事合并成一项。** 隔离结论会直接改变部署形态（同容器多进程 vs 每身份独立容器），而部署形态又决定资源模型。分开做会得出互相矛盾的结论。

方案 §5.3 自己写了"独立进程不是强沙箱"，解法是"独立 OS 身份及目录权限"。这句话的工程含义要摊开：控制服务必须能以**不同 uid** 拉起子进程，意味着容器不能是 rootless-by-default，需要 `CAP_SETUID` 或等价能力。这是**部署形态的硬约束，应在 P0 定死**，不能拖到 P5 容器化时才撞上。

**已有的一个实测点**：当前单个 runtime（含 ORYH Host 插件、全部领域服务、一个浏览器会话）空闲 **RSS ≈ 119MB，CPU ≈ 0.2%**。这是 macOS 上单次空闲测量，**不是容量模型**，仅用于确认数量级——按此底噪 20 身份空闲约 2.4GB，"单容器"并非显然不可行。

> **2026-09-12 更新：per-uid 由"待验证的要求"变成硬前提。** 客户端现在按 ORYH 的既有方案下载 personal skill bundle，落到 `<agentsHome>/skills`（`DSH_AGENTS_HOME`，默认 `~/.agents/skills`），文件里带着**该人的 `ORYH_API_KEY` 明文**（见 [ADR-0009](adr/0009-chat-pane-is-a-generic-oryh-agent.md)、[Skills 装载](23-oryh-skills.md)）。同一个 skills 根就是同一个人的凭据，共享该目录等于共享身份。多身份部署必须给每个身份独立的 `DSH_AGENTS_HOME`，并由 OS 目录权限强制，S0-2 下面"同 uid 场景能复现跨目录读取"这一判据因此必然成立——它现在读的是凭据，不只是会话数据。

> **2026-09-13 更新：攻击面要按"有 shell"来测。** agent 现在持有 `bash`，而且执行的是租户管理员编写、随时可改的 skill 脚本（[ADR-0009](adr/0009-chat-pane-is-a-generic-oryh-agent.md)）。因此交叉访问不能只在 Remote/接口层试——**必须让身份 A 的 agent 自己跑一条命令去读身份 B 的目录**，那才是真实攻击者的能力。同理，"任意路径注册被拒"这类 Profile 层判据不再是边界，只是深度防御。

**步骤**

1. 起 4 个身份：A1、A2（同租户不同用户）、B1（与 A1 同自然人、不同租户）、B3。
2. **先在同一 OS 用户下**跑一遍交叉访问，用以证明风险真实存在。
3. 再以**不同 uid + 目录权限**跑一遍。
4. **用 agent 的 shell 复测同一组访问**：在 A1 的 Chat 里让它读 B1 的 `DSH_AGENTS_HOME/skills`、数据根与 Session 目录。这一步取代"仅接口层尝试"作为主判据。
5. 资源梯度：4 / 10 / 20 个同时活跃身份，分别跑纯页面查询、流式 Chat、混合负载。
6. 单独测量"只读业务访问"的 runtime 底噪占比。
7. **skill bundle 的磁盘与同步开销**：单身份 bundle 的目录数、文件数与体积（当前租户实测 35 个技能目录、52 个 Python 文件），乘以 20；再测"租户管理员改一条业务逻辑后 20 个身份同时重连"的拉取表现。

**成功判据（全部满足）**

| 判据 | 观测方式 |
| --- | --- |
| 跨身份的列举、读取、订阅、导出、取消全部被拒 | 逐接口尝试，覆盖原生 Session/Workspace/附件 |
| 拒绝响应不泄漏资源是否存在 | 对比"存在但无权"与"不存在"的返回 |
| 同 uid 场景**能复现**跨目录读取 | 证明 per-uid 是要求而非建议；复现不出则重新审视测法 |
| per-uid 场景下跨目录读取被 OS 拒绝 | 同样的读取操作返回 EACCES |
| **A1 的 agent 用 bash 读不到 B1 的 skills 根** | 在 A1 的 Chat 里实际执行；读到即等于拿到 B1 的 `ORYH_API_KEY`，属于阻断级失败 |
| 给出 20 身份的 skills 磁盘占用与同步并发表现 | 目录数/文件数/体积 × 20；管理员改一次定义后的同时拉取 |
| 直接调用原生插件安装/任意路径注册被拒 | 绕过前端直接打接口 |
| 给出 4/10/20 的资源曲线与单 runtime 底噪区间 | RSS、启动时间、事件循环延迟、fd 数 |

**停止条件**

- per-uid 在目标容器形态下无法实现 → 改为**每身份独立容器**，重估部署与编排成本；不得为了坚持"单容器"降低隔离要求。
- **agent 的 shell 能越过 uid 边界**（容器内网络出口、共享挂载、宿主接口等任一条）→ 直接按"每身份独立执行容器"推进，不再论证单容器方案；这是执行租户代码的必然代价，见方案 §5.3 同日期注记。
- 20 身份资源超出单机预算且空闲回收吸收不了 → "单容器"目标降级为"单产品实例 + 多 worker"，方案 §11 已预留该路径。

**产出**：隔离验证报告、容量基线、**部署形态结论**（单容器 / 多 worker / 每身份容器）。

## S0-3 ORYH 授权契约

**为什么最早启动。** 它依赖 ORYH 侧配合，等待时间不由我们控制；而且若 ORYH 不支持服务器形态的回调与客户端注册，登录方案需要对方排期，P1 直接阻塞。

方案 §2 已指出：ORYH 是授权码 + PKCE、不透明访问令牌、轮转刷新令牌；**不能假设它是 OIDC，不能从 JWT claims 推断身份**。

**步骤**

1. 核实 OAuth 客户端注册方式、允许的回调、是否支持非 loopback 的服务器回调。
2. 核实 membership 能否**权威枚举**；不能则确认"逐租户分别授权"的实际交互形态。
3. 核实注销与撤销语义，以及 refresh 轮转在并发下的实际行为。
4. 核实身份接口返回的稳定字段，确认能否作为 principal 主键。

**成功判据（全部满足）**

| 判据 | 观测方式 |
| --- | --- |
| 在非 loopback 回调下完成一次真实授权码+PKCE 登录 | 端到端跑通，取得稳定身份 |
| membership 是否可枚举，有明确答案 | 据此定下 tenant 切换交互，不推测 |
| 并发刷新行为已知 | 同时发起两次刷新，记录实际结果 |
| 撤销后旧令牌确实失效 | 撤销再调用 |
| principal 主键字段确定 | 写入字段定义 |

**停止条件**

- ORYH 部署不支持服务器回调或客户端注册 → 登录需 ORYH 侧改造，纳入对方排期，**P1 阻塞**，先不要实现依赖它的功能。
- membership 不可枚举且逐租户授权的交互不可接受 → 回到产品决策，重新定义多租户切换体验。

**产出**：认证契约说明、Principal 字段定义、tenant 切换交互决策。

## 整体退出条件

四项全部达标，且以下三件事有书面结论，才进入 P1：

1. **代理形态**：路径前缀还是子域，附带部署前提。
2. **部署形态**：单容器多进程（含 per-uid 方案）、单实例多 worker，还是每身份独立容器。
3. **登录形态**：能否直接对接现有 ORYH 授权，还是需要对方改造。

方案 §9 的原话仍然适用，这里重复一次作为验收纪律：**阶段之间以验证结果推进，不以包创建完成或首页打开作为完成标准。**

## 估算说明

不在本文给出人天数字。方案 §12 明确"时间估算在 P0 后按实际改造面更新"，而 S0-1 与 S0-3 的结果会显著改变后续范围——在它们出结果前给出的估算是假精度。S0 自身的规模可以先按"四项并行、以 S0-3 的外部等待为关键路径"来安排。
