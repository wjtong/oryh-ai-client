# ORYH Client 传统交互与 AI 协作审查

日期：2026-09-08。范围：本仓库客户端代码、产品与安全设计，以及 `/Users/wtong/git/calwbiz` 中的身份、权限和相关业务接口。此次为源码审查与本地伪造数据验证，未登录测试环境，未执行真实业务写入。文中建议不代表已实现。

## 结论

现有产品原则正确：传统界面与 AI 共用 Operation，服务端保存事实并执行授权和业务约束。当前实现是三个只读入口、设备连接和结果保存组成的验证版，尚未形成完整的传统业务客户端，也未接通 AI 会话、工具或提交流程。下一阶段应完成一个双入口业务闭环，而不是先扩大聊天能力或复制所有 ERP 页面。

用户应能通过列表、表单和按钮独立完成高频工作，也能通过自然语言、附件和上下文让 AI 帮助理解、填表和编排。两条路径操作同一份草稿、调用同一组业务能力、接受相同授权和审计。

## 已确认的代码问题

### P1：跨地址重定向携带访问密钥

`packages/core/src/http.ts` 的 `send()` 注入 `X-API-Key`，但未限制 fetch 重定向。使用两个本地 HTTP 服务与合成密钥复现：第一个地址返回 302 后，第二个地址收到同一密钥。如果服务或代理返回跨地址重定向，密钥会离开已绑定的 origin。refresh 和 device token 请求也应统一审查重定向策略。

建议默认拒绝认证请求的重定向；需要更换部署地址时通过显式重新连接处理。生产地址要求 HTTPS，测试 HTTP 作为明确的开发配置。验收应覆盖跨 origin 302/307/308，确保第二个地址收到零凭据。

### P1：企业切换后接收旧请求结果

`packages/workspace/src/index.ts` 的 `run()` 在发请求前捕获 connectionId，返回后只与该旧值比较，随即更新 currentResult。顶部企业选择器允许在请求期间切换。复现顺序：A 发起请求 → 切到 B → A 返回；最终 activeConnectionId 为 B，而 currentResult.connectionId 为 A。reuse、刷新保存操作和连接相关的异步加载也需要同类保护。

建议以连接和视图 generation 约束状态提交，切换时清除旧状态并取消可取消的请求。每个异步结果只有仍属于当前 generation 才能进入 UI 或 AI 上下文。禁用切换按钮只能作为体验优化，不能替代状态层约束。还应保证切换验证失败时内部活动连接与界面显示一致。

### P1：断开连接后仍可读取旧业务缓存

`packages/core/src/operations.ts` 的 reuse() 仅比较结果内保存的 connectionId，不检查连接是否存在或仍获准使用；Host.disconnect() 不清理 OperationExecutor 的结果 Map。移除连接后继续调用 reuse() 已成功返回原项目数据。Controller 的结果复用接口仍可到达这一路径。

建议断开或冻结连接时清除相关缓存、阻止在途请求重新写回；复用前验证连接状态及结果 Operation 类型。若未来保留离线缓存，应作为具有独立授权、时间标记和保留策略的功能，不能借用已断开的在线连接。

### P2：首次验证依赖已有构建产物

根 package.json 的 typecheck 只先构建 core，web 却通过 workspace 包导出的 lib 类型检查。没有 workspace/lib 时，`corepack pnpm run verify` 失败于 `Cannot find module '@oryh/ai-client-workspace'`，继而出现隐式 any。建议使 verify 在全新依赖安装后的工作区可独立运行，按依赖顺序生成所需声明或使用明确的 TypeScript 项目引用。

## 接入 AI 前必须补齐的边界

- **有效权限。** 服务端 `app/api/auth.py:me()` 返回 permissions，客户端 decodeIdentity() 丢弃了该字段，listOperations() 返回固定目录。应依据服务端有效权限显示能力与工具，eligible Skill 只决定业务指引适用性；所有写入仍由服务端最终校验。当前固定只读目录本身不等于服务端越权。
- **本地请求身份。** 本地 API 只在 Origin 存在时检查它，没有 Host 校验或窗口会话认证。本次没有进行浏览器 DNS rebinding 攻击验证，但代码不能把“请求来自 loopback”当作“由已解锁用户授权”。应校验 Host/Origin，并将接口与受控窗口会话、本地解锁状态绑定。
- **安全状态机。** Keychain 储存不等于 user presence。实现 Connecting、Verifying、Ready、Locked、ReauthenticationRequired、Disconnected，统一约束传统操作、AI 工具和缓存读取。验证失败需要撤回已有 Ready 状态。服务端设备吊销与删除本地凭据要明确区分。
- **受控的 DSH Profile。** 当前 dsh-host 只提供开发 Controller，使用内存凭据，没有生产 Remote 或 Agent 工具接入。正式 Profile 应只暴露受约束业务工具；不得通过通用 shell、任意 HTTP、文件系统或自修改插件绕过 Operation。
- **有界数据与传输。** 三项列表请求没有指定分页；当前服务端在不传 page/size 时返回全量。应增加参数化筛选、分页、超时、取消和缓存容量限制，再设计发送给模型的字段、条数、用途和保留策略。
- **写入保障。** 现有 Operation 仅支持 GET，没有 proposal、确认凭据、版本冲突处理、持久执行记录或恢复逻辑。服务端部分账务操作有幂等处理，不能据此假定所有业务接口都安全可重试。写操作必须逐端点核实其事务、幂等和并发约束。

## 产品方案

### 以业务对象为主界面

首页呈现我的待办、在途申请、最近工作和固定视图。进入对象后，主区域展示原始事实、结构化表单和动作；上下文侧栏提供 AI 解释、附件识别、检查和下一步建议。AI 不可用时，列表、编辑、校验、提交与状态查询仍可用。复杂配置和全局审计提供准确的 Console 深链。

避免让用户在“传统模式”和“AI 模式”之间维护两套状态。用户在同一份费用草稿中既能改金额，也能说“按日期整理这些票据”；AI 的改动应显示来源、不确定字段和差异，用户可以逐项修改或撤销。

### 按动作后果决定自动化程度

| 动作 | AI 的权限 | 用户控制与系统约束 |
|---|---|---|
| 查询、筛选、解释 | 在当前任务授权的数据范围内执行 | 不逐条弹确认；展示来源、更新时间和范围 |
| 填写与修改本地草稿 | 可以生成和修订 | 展示差异、不确定项，支持手动编辑和撤销 |
| 创建服务端草稿 | 经明确授权后执行 | 告知已产生服务端记录，以服务端规则校验 |
| 提交、审批、付款、记账、权限修改 | 可以准备建议和参数 | 用确定性界面确认具体对象、动作和关键字段；最终由服务端授权 |
| 长时或批量任务 | 在明确范围、额度和期限内准备或执行获准动作 | 可暂停；逐项回执；部分失败可恢复，扩大范围重新授权 |

不要让每个读取都请求批准，也不要用一次模糊的“允许 AI 处理”覆盖未来所有业务写入。正式审批必须是审批人的明确动作；工具确认不等于审批事实。

### 共用执行路径

传统表单与 AI 输出都先形成类型化 proposal。Host 校验其来源连接、Operation 版本、参数、风险、权限和对象版本，再决定直接执行还是展示确认。确认必须绑定该 proposal 的不可变内容；字段变化使旧确认失效。执行使用可追踪的 operation id，明确区分成功、失败和结果未知；网络超时不显示成功，也不盲目重放。

审计区分谁提出、谁确认、用什么身份执行、服务端保存了什么。界面区分原始事实、AI 判断、未提交草稿和已执行结果。附件或 Skill 中的文字不能授予工具权限、改变连接或替用户确认。

## 建议实施顺序与验收

1. 修复上述 P1，补齐全新工作区 verify、本地接口身份、安全状态和异步生命周期回归。
2. 完成一条传统费用申请流程：列表 → 明细/附件 → 可编辑草稿 → 校验 → 明确提交 → 服务端回执与状态跟踪；无需模型即可完成。
3. 为同一草稿接入 AI 材料识别、补全、解释与规则检查。先从只读工具和草稿建议开始，再复用已经验证过的写 Operation。
4. 加入审批辅助、参数化保存视图和跨单据业务线程。自动化授权和批量执行在单项写入可恢复之后实施。

验收以用户能够完成工作和系统拒绝错误动作衡量：模型不可用仍能提交；切换企业时旧结果不进入当前 UI/模型；恶意票据无法触发写入；用户修改字段后旧确认不可执行；提交超时可查明结果；权限撤回后工具与最终写入一致拒绝；审计能够关联 proposal、确认、执行和服务端回执。
