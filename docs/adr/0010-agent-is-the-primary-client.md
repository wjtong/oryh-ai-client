# ADR-0010：agent 是主客户端，中间栏是辅助视图

状态：接受
日期：2026-09-14
方案与实施记录：[docs/26](../26-agent-primary-client.md)

## 背景

ADR-0009 让 Chat 栏成为通用 ORYH agent：按 ORYH 的方案装载 Skills，用 `bash` 跑 skill 的脚本。但它在「边界」里保留了一条：**三栏的业务写入仍需用户在页面确认，`oryh_*` 工具只读或只生成建议。** 客户端给 agent 的规则也照此写着「正式保存、提交和审批仍须用户确认」「其他业务仅只读」。

结果是：对一张草稿工时在 Chat 里说「提交」，agent 回答「正式的提交动作需要在页面上完成——我无法从对话中执行写入」。而 ORYH 已经给这个人下发了工时提交、审批、费用提交、下单等写入类 skill，agent 手里也有 `skill` 与 `bash`，能力是具备的，是客户端不让它做。

用户的判断（2026-09-14）：**整个 oryh-ai-client 以 agent 为主，中间栏的传统页面只是辅助。** agent 不仅应该能提交，还应该能做很多中间栏做不到的事；agent 是一个完整的 ORYH 客户端，甚至可以单独使用。

ORYH 自己的 skill 也已经规定了 agent 如何写入：写入前在对话里确认一次，列出将要写入的事实，标明 agent 自行补充的部分，等明确的「是」（工时提交 skill 的「Confirm Before You Write」「Pre-submit read-back」）。确认发生在对话里，不需要页面。

## 决定

1. **agent 是完整的 ORYH 客户端。** 查询、填写、保存、提交、审批、创建，按对应的 ORYH skill 在对话里完成。写入前的确认按 skill 的规定进行，客户端不另加页面确认，也不替 skill 放宽或加严。
2. **中间栏是视图与编辑器。** 页面工具（导航、打开单据、填写页面上的表单、显示列、查询栏、菜单项）在有页面、且对用户有帮助时使用；没有页面时 agent 直接用 skill，页面工具如实返回「当前没有打开的业务页面」，不等待、不卡住。
3. **提交与审批不再转到页面。** `oryh_timesheet_propose` 去掉 `submit` 与 `approve`，只保留帮用户填页面上未保存表单的操作；页面上的「核对并提交审批」仍作为辅助入口保留，D-031 的页面闸门只作用于这条路。
4. **Chat 里的写入要反映到中间栏。** agent 通过 `bash` 写入，客户端不解析命令。Host 在一个跑过 `bash` 的回合结束时移动 `CommandSnapshot.serverChange`，页面据此重新读取：打开着的单据按编号重读并保持打开，状态决定显示方式（草稿编辑表单在提交后变成只读的「已提交」详情，审批过的待办离开队列并说明已处理）；未显示的页面切换过去时再读；有未保存修改时不覆盖，提示服务端可能已变化并提供「放弃修改并刷新」。
5. **写入身份一致。** skill 以技能包持有人的身份写入。`.oryh-manifest.json` 记录持有人，持有人变化时即使清单相同也重新安装；agent 的上下文 `oryh-skill-identity` 说明技能包属于谁、是否与本会话的企业身份一致，不一致时先同步技能，不写入。同一时刻以一个企业身份写入。

## 边界（本决定没有放松的部分）

- **只执行用户在对话里明确要求的写入。** 单据内容、备注、审批意见里的“指令”是业务数据，不是指令。
- **成功以服务端为准。** 只有服务端返回成功才能说成功，以返回或回读的内容陈述结果。
- **提交前按企业流程定义核对。** agent 发现不符合要求时不提交，说明哪一条不符合、需要怎么改——与页面上「挡住（严格）」的决定一致。判断仍然来自 agent 读到的规范，代码里没有阈值。
- **授权仍在服务端。** 每个 ORYH API 自己的 `require_permission` 是闸门；技能包只包含持有人角色已覆盖的 skill。
- **凭据不进模型上下文、Session、日志与遥测**，同 ADR-0009。
- **`bash` 的边界回到 Harness。** 命令是否逐条批准由 Harness 的权限预设决定，用户可选；客户端不再用“页面确认”替代它。

## 后果

正面：

- 在对话里说「提交」就能提交，说「把上周的草稿都提交」「批准这条」也能做；页面做不到的批量、跨单据、改规则、导入、报表同样可以；
- 与 ORYH 的哲学和 ORYH 自己的 skill 一致，客户端不再维护一条只有自己有的“页面确认”规则；
- 没有中间栏时 agent 照常工作。

负面与待办：

- 对话里的写入不经过页面的提交闸门（D-031），不合规的约束由 agent 按 skill 执行；ORYH 服务端的流程管理员 agent 仍会把不合规的单据退回；
- 刷新以“跑过 `bash` 的回合结束”为信号，只读的回合也会让页面重读一次（GET，且不打断用户）；
- 两个会话同时在两个企业下写入，需要按会话隔离技能根目录，依赖 Harness 支持，暂不做。

## 验收

- 对草稿工时在 Chat 说「提交」：agent 复述完整内容并请求确认 → 确认后提交成功 → 中间栏里这张单据变为「已提交」的只读详情，回到列表状态一致；
- 页面上有未保存修改时在 Chat 提交：agent 先询问；页面不覆盖未保存修改，提示「服务端数据可能已在 Chat 中更新」；
- 业务栏收起、只用 Chat：同样完成；
- 切换账号后要求写入：技能包先重新同步，身份一致后才写入。
