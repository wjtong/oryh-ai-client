# ADR-0008：领域保持为库，不拆为可独立启停的业务插件

状态：接受
日期：2026-09-12

## 背景

`plugin-split` 把工作区从 5 个包拆到 14 个：`foundation`、`store`、`pages` 以及 records、timesheets、todos、projects、expenses 五个领域包。[2026-09-12 的评审](../18-plugin-split-review-2026-09-12.md) §4 指出，这个结果**不等于**各领域可以独立启用、停用和卸载，并要求先做产品决策，再决定是否继续抽包。

核查代码确认评审判断成立。领域目前是**编译期模块，不是运行时单元**：

- [`index.ts`](../../packages/dsh-host/src/index.ts) 中 `createLocalOryhRuntime()` 一次性构造全部服务，`apply()` 一次性 `ctx.provide`。一个 Harness 插件 `oryh-client-host` 提供所有领域。
- [`local-runtime.ts`](../../packages/core/src/local-runtime.ts) 中每个领域都是 `host.createXxxRemote(...)`，共用同一个 `OryhClientHost`（钥匙串、连接存储）与**同一个 fetch 生命周期 AbortController**。
- `OryhRemote` 是一个类、44 个 `@Remote` 方法，横跨所有领域。
- 16 个模型工具全部经 `chat.install()` 注册。

评审提出的产品问题是"某企业是否只启用库存、不启用工时"。这个问法混合了三种诉求，其中一种**已经实现**：

| 诉求 | 现状 |
| --- | --- |
| 某个**用户**不能使用工时 | 已实现。`canAccessPage` 控制菜单入口，`requirePage`/`requirePermission` 在 `operations.ts`、`business-chat.ts` 与各领域 service 做服务端拦截，并有撤权后 Remote 查询被拒的测试 |
| 某个**企业**未购买工时模块 | 未实现，需要与用户权限**正交的第二个轴** |
| 某个**企业**的 ORYH 服务端没有工时 API | 未实现，且更可能需要探测而非配置 |

按模块售卖与按租户裁剪服务端能力当前都不是已确认的商业需求。

## 决定

1. **ORYH 工作台按整体交付。** 组成保持"两个 Harness 插件（`@oryh/dsh-host`、`@oryh/dsh-client`）＋ 多个领域库"，领域库是编译期依赖，不是可独立装卸的运行时插件。
2. **不以包数量作为模块化的完成指标。** 只有当某个包带来真实的维护、测试或依赖收益时才继续拆；不为对称性拆包。
3. **不抽取 `@oryh/dsh-connections` 与 `@oryh/dsh-workbench`。** 在没有独立启停需求的前提下，它们只会增加组装层次而不改变能力边界。若将来抽取，必须先写清职责再动代码。
4. **不引入动态领域注册框架。** 不为尚未确认的扩展预先建立服务/Remote/工具/页面的注册与卸载契约。
5. **业务授权继续在服务层执行，菜单可见性只是展示。** `canAccessPage` 决定入口显示，服务端的 `requirePage`/`requirePermission` 决定数据访问；任何时候都不得以"菜单已隐藏"替代服务端检查。
6. **若将来引入按租户的模块启停，它必须是独立于用户权限的第二个轴**，并且同样在服务层执行，不得与 `PAGES` 的权限规则合并成一张表。

## 后果

正面：

- 省掉本阶段最贵的一块改造：44 个 `@Remote` 方法拆成按领域的多个 Remote，会改变生成产物与客户端 `remote.oryh.*` 命名空间；而 typert 生成是按包进行的，领域越多，生成面越大——这与**尚未进入上游**的外部 Remote 补丁叠加，会放大补丁失效的暴露面（见 [迁移记录](../14-dsh-plugin-migration.md) 与 `patches/deepseek-harness-external-remote.json`）。
- 已经拿到的收益（领域边界、窄结构接口、随领域迁移的单元测试）全部保留。
- 按用户权限的裁剪已经可用，覆盖"某人不该看到工时"这类最常见诉求。

代价：

- 单个 Harness 插件的 `apply()` 仍是全领域组合根，新增领域会继续让它变长。
- 领域之间共享一个 fetch 生命周期：`oryhAbort` 中止的是全部在途请求，没有按领域的中止粒度。
- 若商业上出现按模块售卖，本 ADR 需要重新评估，届时改造成本高于现在就做。这是**明确接受**的风险，理由是当前需求不存在，而按需求出现后再做可以由真实约束指导设计。

## 未选择的方案

### 继续拆成可独立启停的领域插件

拒绝。需要先定义服务注册与卸载、Remote 拆分、工具撤销、命令等待的取消、页面登记表动态化、已打开页面与加密草稿的处理等一整套契约，而驱动这些契约的产品需求尚不存在。评审自身也提醒不要为可能的扩展提前引入过重框架。

### 保留领域库，但先把 `dsh-connections`、`dsh-workbench` 抽出来

拒绝。在不做独立启停的前提下，这两个包只是把同一组装逻辑换个位置。评审的措辞是"职责应先写清，再决定是否抽包"——职责写清之前抽包，等于先做了决定。

### 用页面登记表承载模块启停

拒绝。`PAGES` 表达的是用户权限派生的入口规则。把租户模块启停并入同一张表，会让"禁用模块"退化为只隐藏菜单，而 Remote 仍然服务数据。

## 重新评估条件

- ORYH 开始按模块售卖，或出现"某企业只启用部分业务模块"的合同要求；
- 不同租户的 ORYH 服务端能力出现实质差异，客户端需要按租户裁剪而非按用户权限裁剪；
- 单个 Host 插件的组合根规模开始造成真实的维护或启动问题；
- 需要按领域独立中止在途请求、或按领域独立升级；
- 外部 Remote 补丁进入上游，使按包生成的成本显著下降。
