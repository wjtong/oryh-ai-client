# ADR-0004：确定性业务操作优先于模型调用

状态：接受
日期：2026-08-19

## 背景

如果 ORYH AI Client 只是让用户把每个请求重新输入聊天框，再让模型每次生成 API 调用，它会产生不必要的延迟、成本和不确定性，也无法形成真正的业务客户端体验。“我的待办”“项目列表”“刷新刚才的结果”等操作的意图和参数已经明确，不需要推理。

另一方面，给页面按钮、业务列表和 AI Tools 分别实现 API 调用会产生权限、错误、重试、结果和审计语义漂移。保存模型生成的 TypeScript、Shell 或 `curl` 作为重跑程序又会扩大执行面和版本兼容风险。

## 决定

1. ORYH Client 是“确定性业务应用平面 + Agent 平面”的混合客户端。
2. 每项有界查询或业务命令实现为一个带稳定 id/version、类型化输入、规范输出、权限、风险和 presentation 的 Operation。
3. 页面、按钮、最近操作、已保存视图和 AI Tool 是同一 Operation 的不同 Consumers，不各自实现网络调用。
4. 意图和参数已知时，UI 直接运行 Operation，不创建隐藏 Prompt、不启动 Agent loop、不调用模型。
5. 只读 Operation 成功后生成 tenant-bound receipt，可用于刷新、再次运行和固定为视图；receipt 不含凭据、任意 endpoint 或可执行代码。
6. 用户选择“就此询问 AI”时，才把其选择的有界最新结果作为 model-visible 且 logged 的 Session 事件交给 Agent。
7. Mutation receipt 不能直接重跑。用户只能以历史结果为模板创建新 proposal，并重新读取关键事实、校验权限和确认。
8. 缓存和最近结果用于快速展示，不成为业务事实源；陈旧状态和刷新时间始终可见。

## 后果

正面：

- 高频操作更快、成本更低，并在模型不可用时仍可使用；
- 同一个业务动作在 UI 和 AI 中具有一致权限、错误、审计和渲染；
- 用户可以一键刷新或复用只读查询，不需要重复描述；
- Prompt injection 可利用的模型调用和通用执行面减少；
- 可以准确度量哪些任务真正需要 AI。

代价：

- 需要设计和维护 Operation registry、receipt、版本迁移和业务视图；
- UI 和 Tool adapters 需要围绕同一 canonical result 协作；
- “就此询问 AI”需要显式的结果裁剪和 Session 事件；
- 不能依赖一个通用聊天框快速覆盖所有产品体验。

## 未选择的方案

### 所有操作都通过聊天 Prompt

拒绝。对已知操作增加延迟、成本和随机性，模型不可用时整个客户端失效。

### 保存模型生成的 API 代码并重复运行

拒绝。代码可能包含陈旧路径、秘密、任意网络行为或不受当前策略约束的逻辑，升级和审计困难。

### UI 和 AI Tool 各自实现 API 调用

拒绝。认证、错误、幂等、权限和结果容易漂移，测试成本翻倍。

### 只缓存结果，不保存 Operation 描述

拒绝。用户只能看到旧数据，不能可靠刷新相同筛选；缓存也容易被误认为事实源。

## 重新评估条件

Operation 作为共享执行来源不计划取消。具体 receipt 格式、缓存策略和哪些模块提供一级入口可以依据使用数据调整；跨租户聚合仍需独立架构，不能让 receipt 跨 connection 重跑。
