# 工时录入与经理审批

## 用户操作

- 左栏 **我的工时**：读取本人全部工时单；新建时填写期间、原始工作说明，以及逐日的小时、类型、项目、任务和备注。日期与每日合计在 Host 校验。选择企业已有的工时类型，不自动补齐或取整工时。
- **核对并保存**先调用 ORYH `validate_only=true`，显示整单核对内容，再由用户确认原子创建服务端草稿。创建和提交是两个独立动作。
- 打开已保存的工时单可以新增、修改或删除明细，每次独立核对和确认。已保存明细的日期不可直接修改。编辑和提交按钮使用企业公开对象定义中的状态机；服务端仍执行最终权限与状态检查。
- **核对并提交审批**重新读取整单，显示每条明细、每日合计和期间合计。企业工作流自然语言要求可在页面展开查看。
- 左栏 **工时审批**只读取分配给当前员工的、未完成的工时审批待办。打开后显示申请人编号、明细和审批历史；选择通过、拒绝或退回修改并填写意见，再核对确认。
- 经理动作仅追加审批事实，使用待办中的轮次与节点，不直接改变单据最终状态或指定下一审批人。服务端同时处理当前待办，后续由 ORYH 工作流推进。
- **执行记录**保留本机加密的确认和写入结果。断网时不自动重发；使用“核对服务端结果”查找已落地记录。不能证明结果时继续保持待核对，由用户在 ORYH 或联系管理员核查。

## Harness 集成与边界

全部能力属于现有外部插件：`@oryh/dsh-host` 提供 `oryh.timesheet*` 的 Typert Remote，`@oryh/dsh-client` 在既有业务 Slot 中呈现表单和列表；没有新增 HTTP 监听器、独立应用壳或模型调用循环。生成的 Gateway 描述符校验输入和返回值。插件卸载释放服务并终止在途请求。

Host 绑定当前企业、用户和员工；模型、浏览器均不传入员工身份或审批人。确认仅供浏览器使用，不注册为 Agent 工具。普通 chat 继续使用 Harness 原生模型配置；自然语言填工时和自动业务工具尚未启用。

持久记录采用独立 Keychain 密钥和 AES-GCM 加密，修订通过 compare-and-append 独占落盘。单个 Host 中确认请求串行执行，写入前重新比对整单、待办和状态机，消费五分钟有效的一次性确认。该 Profile 仍是单用户开发组合，不应让多个 Host 同时共享同一个数据目录。服务端目前没有整单 ETag/条件写入接口，最后一次读取和写入之间的外部并发变化最终依赖 ORYH 自身的权限、状态和节点约束。

## Chat 工时协作（2026-09-09）

打开“我的工时”或“工时审批”后，外部 Client 通过 Harness 原生 Session 选择源和生成的 Remote 关联当前页面。`oryh_timesheet_read` 读取当前员工可见的工时/审批队列、企业工时类型和项目、当前单据，以及浏览器未保存表单。`oryh_timesheet_propose` 使用 Harness 结构化参数定义生成 create、submit、add-line、edit-line、delete-line 或 approve 建议。

建议只保存在 Host 内存，由同一认证 Remote 同步到中间栏。填写建议可应用到现有工时表单，其他操作进入现有 `timesheetPrepare` 核对流程；最终仍调用原有浏览器确认入口。模型拿不到确认 token，也没有 prepare/confirm 工具。用户修改输入、切换页面或 Session 后，旧版本建议不能应用；页面身份沿用持久化的企业/用户/员工绑定。工具不接受 Connection、员工或 URL 参数，单据和审批待办必须在当前员工的可见列表中。

例如：“帮我填写 2026-09-09 的正常工时，项目是装配产线自动化技改，工作内容是产线调试，8 小时。”模型先读取真实项目与工时类型，再生成可核对的填写建议；未知日期、重名项目等仍应询问用户，不自动猜测。当前开放的是上述业务操作，并非任意 API 或越权操作。

验证：全仓 82 项测试及构建/类型检查通过；新增测试覆盖页面版本失效、跨页面/单据/审批范围拒绝、项目与小时校验以及建议不调用 prepare/confirm。真实 DeepSeek 会话通过原生工具查询配置并生成 2026-09-09、正常工时 2 小时的建议，应用后真实表单各字段正确。测试表单已放弃，没有保存、提交或审批业务记录。

## Chat 主导交互（2026-09-09）

当前布局为左菜单、中间 Harness 原生 Chat、右业务视图。业务导航桥通过公开 Slot owner 回调驱动现有根 store，Session 在连接就绪后即可使用 `oryh_open_timesheet`，不必先选菜单。导航工具只发出短时导航命令，浏览器打开真实工时编辑器并同步状态后才返回成功；运行中仅允许该命令对应的同企业工时导航，不能借此切换企业、待办或审批目标。

`create` 填写操作现在自动更新未保存表单，不再要求点击“应用”。字段仍携带版本，手动修改、Session 切换、离开页面或取消会使迟到更新失效。工具等待浏览器状态回传，区分“已填入表单”和“已保存到服务器”。允许分步填写未完成表单，最终完整性校验仍由原有保存/确认流程负责。其他修改已保存记录、提交与审批操作仍进入核对确认。

验证：87 项测试通过；真实原生会话从待办页面发起打开工时表单，再通过后续消息把小时从 2 改为 3、更新任务，未点击应用，其他字段保持不变。1470px 桌面验证 Chat 在中间、业务视图在右；窄屏默认 Chat 并可切换表单。验证没有保存或提交数据，测试表单已放弃。

## Chat 打开已有工时（2026-09-09）

`oryh_find_timesheets` 从已绑定企业查询本人工时和分配给自己的审批候选。模型按姓名、期间或编号匹配，候选不唯一先询问；不提供任意员工查询或跨租户入口。`oryh_open_timesheet` 接受查到的 `headerId` 和审批候选的 `todoId`，Host 先调用共享详情操作验证访问权限，再通过已有 Slot/store 导航到本人或审批页面。只有浏览器成功打开指定记录并回传对应导航编号后才报告成功；有未保存修改时拒绝替换。

详情的 `canEdit` 由 Host 读取 `/auth/me` 的实际 `timesheet.submit_own` 权限、当前员工归属与企业状态机共同计算，不由模型指定，也不凭角色名称推断。本人的可编辑单据直接显示明细输入，每次核对保存一条明细，保存后重新读取该单据；其他情况展示只读内容。审批操作仍独立于内容编辑，并继续使用既有核对/确认流程。

验证：构建通过，当前 99 项测试通过（Core 62、Host 19、Workspace 9、Client 9）。真实 Harness/DeepSeek 会话从待办页打开本人 2026-08-24～2026-08-28 草稿，右侧直接呈现五条明细编辑表单，工时类型和项目选项正常加载；再按姓名打开何丽萍 2026-06-22～2026-06-28 已提交工时，右侧为只读内容及独立审批区域。测试未保存、提交或审批，原浏览器未保存表单保留在原标签页。
