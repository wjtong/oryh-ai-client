# ORYH AI Client 产品需求

状态：规划基线
日期：2026-08-21
目标读者：产品、设计、客户端工程、ORYH 后端工程、安全与测试

## 1. 产品愿景

ORYH AI Client 是 ORYH 的第一方优化工作客户端和兼容 Agent 的参考实现，而不是只有聊天框的 ORYH 接入器，也不是使用 ORYH 的必经入口。它把 ORYH 这个 agent-native 企业事实系统投影为“个人企业工作台 + Agent”：对于“看我的待办”“打开项目列表”“刷新刚才的结果”等意图和参数已经明确的操作，客户端直接执行确定性的业务 Operation，不调用模型；用户表达模糊目标、提供非结构化材料或需要判断和解释时，Agent 才负责理解上下文、选择合适的 ORYH Skill、组合相同的业务 Operation 并展示证据与执行结果。ORYH 服务端负责保存真实业务记录并执行权限、租户、生命周期和数据完整性约束。

产品不追求把所有 ERP 页面改成聊天框，而是让最常见的“发现工作—理解业务线程—补齐信息—核对—提交—跟踪”流程在一个可信工作空间中完成，并在需要大规模浏览、配置或审计时无缝进入 ORYH Console。导航和功能模块由当前 capability 与 eligible Skill 动态得出，不把销售、采购、财务或审批身份硬编码成固定角色菜单。

## 2. 要解决的问题

ORYH 已经具备多租户数据、RBAC、业务单据、审批事实、待办、工作流定义、Skills 和审计能力，但通用 Agent 的接入仍存在体验与安全缺口：

- 设备连接、凭据刷新、Skill 同步依赖 Markdown 指令和不同 Agent 的本地环境；
- 用户看到的是通用聊天或编码 Agent，而不是待办、报销、审批等业务对象；
- 通用 Bash/HTTP 调用给模型过宽的执行面，参数、重试和错误处理缺少统一实现；
- Skill 中渲染访问密钥会让秘密进入模型上下文、本地文件和会话记录；
- 多企业用户容易在错误的租户上下文中执行动作；
- Agent 的工具执行确认与企业里的正式审批容易混淆；
- Console 适合管理和浏览，不适合把自然语言、附件识别和多步业务判断组织成一次工作会话。
- 报价、订单、发票、收付款、核销以及申请、审批、待办分散在不同 API 资源中，用户需要一条可追溯的业务线程，而不是自己拼接单据编号。
- 服务端事实、服务端派生值、Agent 依据 Skill 得出的结论和尚未执行的 proposal 容易在自然语言回答里混为一谈。
- capability 决定授权，Skill audience 决定业务指引投放；只看角色名或只看其中一层都会产生错误导航和工具暴露。

## 3. 目标用户

### 3.1 普通员工

查看自己的待办和在途申请，填报工时、费用、请假，预订资源，查询工资单，并修正被退回的记录。

### 3.2 审批人和经理

从待办进入业务记录，查看必要证据和风险提示，记录批准、驳回或退回意见，并跟踪团队提交情况。

### 3.3 业务岗位

销售、采购、财务和运营人员创建与处理报价、订单、采购、发票、收付款、核销、账户余额和主数据。

### 3.4 租户管理员

通过自然语言辅助配置人员、角色、策略、对象类型、工作流和 Skills，查看自动化运行情况；复杂批量配置继续进入 Console。

### 3.5 明确不覆盖的用户

平台运营管理员不通过本客户端执行跨租户管理。Hosted Flow Runner 是服务端自动化负载，不是桌面客户端的交互用户。

## 4. 产品原则

1. **事实归 ORYH。** 客户端不建立会与服务端竞争的业务数据库。
2. **确定性优先。** 已知入口、固定查询、刷新和重复只读操作由应用直接执行，不为同一机械动作重复消耗模型调用。
3. **一项业务能力，一套 Operation。** 按钮、页面、已保存视图和 AI Tool 共享同一个类型化执行实现，不能各自拼 API。
4. **判断归 Skill，机械执行归 Operation。** Skill 保留流程判断、检查项和禁止事项，Operation 负责类型化 API 调用、认证、刷新、幂等和错误映射。
5. **最小权限。** 模型只能看到当前租户、当前角色和当前任务需要的工具。
6. **先预览再承诺。** 提交、审批、付款、记账、权限和批量操作必须显示业务语义明确的确认内容。
7. **多租户显式。** 当前企业始终可见；会话建立后不得隐式切换企业。
8. **失败可恢复。** 网络中断、令牌过期、模型失败和客户端重启不得造成无法判断的重复写入。
9. **可解释但不伪造。** 客户端区分服务端事实、模型推断和用户尚未确认的草稿。
10. **Console 互补。** 客户端处理高频工作，Console 管理和浏览复杂全局数据。
11. **本地优先，企业可管。** 交互进程运行在用户设备上，同时预留企业策略、模型网关、签名更新和诊断能力。
12. **能力派生工作空间。** 模块由 capability、eligible Skill 与租户功能共同决定，不允许通过客户端导航推断或提升权限。
13. **业务线程是投影。** 跨单据视图只能从服务端明确外键和 typed link 重建；缺失关系显示为缺失，不能由模型猜测。
14. **判断带依据。** Agent 结论必须标明采用的 Skill、Policy、Workflow 或对象定义版本，并与原始事实并列展示。
15. **开放而不垄断。** ORYH 继续允许员工选择兼容 Agent；第一方客户端以更好的安全、确定性操作和业务体验取胜。

## 5. 产品目标与非目标

### 5.1 目标

- 用户在五分钟内完成首次连接，并能看到当前企业的个人工作清单。
- 用户一键打开我的待办、项目等高频视图，刷新和重复读取不产生新的模型请求。
- 用户可以从最近结果或已保存视图重新运行一项已知只读查询，而不要求 AI 再生成调用代码。
- 核心员工流程可以从自然语言和附件开始，在客户端内完成创建、核对、提交和状态查询。
- 审批人可以从一个待办卡片完成必要检查并记录正式审批事实。
- 多企业用户不会因历史上下文或默认凭据而写入错误租户。
- 任何密钥都不进入模型可见内容和普通会话日志。
- 业务动作可追踪到用户、租户、会话、工具调用和服务端审计记录。
- 产品能通过外部 DSH Plugins/Profile 演进，减少对 DSH fork 的依赖。
- 用户能从一个待办或单据打开可重建的业务线程，看到其上下游记录、审批事实、当前持有人和未完成义务。
- 工作空间、工具目录与 Skill 内容遵循 `capability AND audience eligibility`，权限或投放变化后按服务端状态收敛。
- 关键业务解释明确区分存储事实、服务端派生值、Agent 结论和未执行 proposal，并保存判断依据版本。

### 5.2 非目标

- 不复制 ORYH Console 的全部列表、配置和报表页面。
- 不在客户端重新实现 RBAC、生命周期、金额校验或工作流状态真相。
- 不让交互客户端承担 Hosted Flow Runner 的无人值守流程推进职责。
- 不把自然语言工作流编译成服务端硬编码 BPM。
- 不向模型开放任意 shell、网络、文件系统或数据库访问。
- MVP 不承诺离线执行或离线排队业务写操作。
- MVP 不支持跨企业聚合或一次请求同时操作多个租户。

## 6. 核心用户旅程

### 6.1 首次连接

1. 用户打开客户端并输入 ORYH 服务地址，默认指向官方服务。
2. 客户端发起 device flow，显示短码并打开浏览器批准页。
3. 用户在 ORYH 页面登录并批准当前设备。
4. 客户端只在主进程接收一次 access token 与 refresh token，写入系统凭据库。
5. 客户端调用 `/auth/me` 获取用户、租户、员工、角色与权限。
6. 客户端同步无凭据 Skill 目录并创建一个绑定该租户的欢迎会话。
7. 首页展示“我的工作”，而不是空白聊天页。

### 6.2 每日工作检查

1. 用户打开客户端或询问“我今天要做什么”。
2. Agent 获取个人未完成待办、逾期事项和本人在途记录。
3. UI 按紧急程度和业务类型展示卡片，并明确数据更新时间。
4. 用户可以打开卡片继续对话、进入正式处理流程或跳转 Console。

### 6.3 提交业务单据

1. 用户描述需求或拖入图片/PDF。
2. Agent 读取相关 Skill、对象定义和工作流要求。
3. Agent 抽取字段并生成未提交草稿，标明来源与不确定项。
4. UI 展示业务预览；用户补充或修改。
5. 客户端创建服务端草稿，必要时上传附件。
6. 提交前再次展示不可忽略的关键字段、总额、附件和目标企业。
7. 用户明确确认后调用提交端点，并展示服务端返回的状态和记录链接。

### 6.4 正式审批

1. 用户从自己的待办进入审批任务。
2. Agent 获取原始单据、明细、附件、审批记录、开放待办及适用 Skill。
3. 根据单据类型展示必须检查的证据，例如报销票据、报价折扣、采购未定价行或收款账户。
4. Agent 可以总结和提示异常，但不得代替审批人作出决定。
5. 用户选择批准、驳回或退回，填写或确认意见。
6. UI 显示“这将写入正式审批记录并完成你的待办”。
7. 客户端记录一个 approval fact，并完成当前用户自己的 todo；不擅自推进后续流程。

### 6.5 多企业切换

1. 用户从全局企业切换器选择另一企业。
2. 客户端保存当前草稿并切换到该企业自己的会话列表。
3. 如果用户试图在当前会话提及另一企业，Agent 只提供切换入口，不调用另一企业工具。
4. 切换后重新计算权限、Skills 和工具目录；原租户上下文不会进入新请求。

### 6.6 重看项目列表

1. 用户第一次通过项目入口或对话查看项目列表。
2. 客户端记录的是规范的只读 Operation 调用描述和结果投影，而不是一段模型临时生成的代码。
3. 结果卡提供“刷新”“固定为视图”“再次运行”和“就此询问 AI”。
4. 用户稍后点击“项目”或“再次运行”，客户端直接用相同的类型化 Operation 和参数请求 ORYH，模型调用次数保持不变。
5. 只有用户要求比较、总结、筛选含义或执行后续多步任务时，才把用户选择的最新结果快照交给 Agent。

### 6.7 日常打开客户端

1. 用户重新打开客户端；在同一已解锁窗口内不重复输入 ORYH 密码。
2. OS 锁屏、睡眠恢复、切换用户或空闲超时后，客户端使用 Touch ID、Windows Hello 或系统凭据完成本地解锁。
3. 客户端加载上次活动企业。access 有效时直接调用 `/auth/me`；即将到期或已过期时先通过单次 refresh 更新完整 credential bundle。
4. `/auth/me` 与本地 tenant/user 匹配后进入“我的工作”。验证完成前，写操作、Agent 业务工具和 Skill 更新保持禁用。
5. 启动时离线则显示明确的“缓存只读”，不把缓存状态称为已登录，不建立离线写队列。
6. refresh 无效、设备被吊销或身份状态改变时才显示“重新连接”，并在系统浏览器重新授权。

### 6.8 追踪一条业务线程

1. 用户从报价、订单、发票、付款、费用申请、采购申请或待办进入“业务线程”。
2. 客户端仅沿 ORYH 返回的显式外键和 typed links 查询相关记录，并分别显示单据状态、审批记录、开放待办和服务端派生指标。
3. 客户端把“当前单据状态”“工作流已通过节点”“当前开放待办”和“定义中可能的后续节点”分开展示。
4. Agent 可以依据当前 Skill 和 Policy 总结阻塞项，但结论标明依据版本，不冒充服务端状态。
5. 用户刷新时直接重新执行有界查询；线程投影可完全从 ORYH 重建，不成为第二套业务数据库。

### 6.9 费用报销到付款

1. 员工提交费用申请及明细、附件。
2. 审批人处理自己的开放待办，记录一个 approval fact，并单独完成本人 todo。
3. 客户端读取租户 workflow/Skill，判断该租户采用直接付款还是报销发票路径，不硬编码唯一流程。
4. 采用发票路径时，线程展示一份费用申请、一个或多个 `reimbursement` 发票、出站付款和 payment applications；同一费用明细不能被重复开票。
5. 财务人员分别确认付款记录与核销，客户端不把二者合并为一个不可审计动作。

## 7. 功能需求

需求使用 `FR-领域-编号` 标识。P0 是 MVP 必需，P1 是首个完整版本，P2 是企业增强或后续扩展。

### 7.1 安装、启动与更新

| ID | 优先级 | 需求 |
|---|---|---|
| FR-APP-001 | P0 | 开发和验收阶段可作为仅绑定 loopback 的本地 Web 应用运行。 |
| FR-APP-002 | P1 | 提供 Windows 与 macOS 签名桌面安装包，负责启动、停止和监控本地 DSH Host。 |
| FR-APP-003 | P1 | 客户端升级必须验证发布签名，并能回滚到上一可用版本。 |
| FR-APP-004 | P1 | 支持官方 ORYH 服务地址和管理员允许的私有部署地址。 |
| FR-APP-005 | P2 | 支持 MDM/企业策略预配置服务地址、模型路由、遥测和更新通道。 |

### 7.2 连接、身份与租户

| ID | 优先级 | 需求 |
|---|---|---|
| FR-CONN-001 | P0 | 使用 ORYH device flow 建立连接，不在客户端直接收集 ORYH 密码。 |
| FR-CONN-002 | P0 | 每个连接把 access、refresh、到期时间、credential id 和 generation 作为一个不可部分更新的 credential bundle 保存到 OS 凭据库。 |
| FR-CONN-003 | P0 | access token 过期时在传输层自动刷新；刷新失败后进入明确的重新连接状态。 |
| FR-CONN-004 | P0 | 通过 `/auth/me` 获取身份、企业、员工、角色和权限，服务端响应是客户端授权展示的依据。 |
| FR-CONN-005 | P0 | 支持连接多个企业，并显示名称、域、用户、角色、连接状态和最后同步时间。 |
| FR-CONN-006 | P0 | 每个会话固定绑定一个租户；会话运行中不允许修改绑定。 |
| FR-CONN-007 | P0 | “断开企业”先幂等吊销服务端当前设备授权，再删除本地凭据；删除该租户本地数据是单独选择。 |
| FR-CONN-008 | P1 | 用户可以查看、重命名和吊销自己的其他设备；吊销其他设备要求近期浏览器认证，且不能看到或操作他人设备和 service key。 |
| FR-CONN-009 | P0 | 日常启动使用本地解锁与连接验证，不要求每次重新进行 ORYH 账号登录或 device flow。 |
| FR-CONN-010 | P0 | 系统锁屏、睡眠恢复、切换用户或连续 15 分钟无客户端交互后，必须通过 OS user-presence API 解锁；不得实现客户端自有密码。 |
| FR-CONN-011 | P0 | 当前活动连接只有在 `/auth/me` 返回的 origin、tenant 和 user 与本地绑定一致后进入 Ready；其他连接惰性验证。 |
| FR-CONN-012 | P0 | 启动验证期间禁止业务写入和 Agent 业务工具；离线时仅提供企业策略允许且有时间标记的加密缓存只读视图。 |
| FR-CONN-013 | P0 | 同一连接的刷新使用跨请求 single-flight，新 access/refresh bundle 原子保存成功后才能恢复等待调用。 |
| FR-CONN-014 | P0 | 设备批准页必须显示企业、账号、角色、官方客户端身份、平台、版本、设备名、短码、期限和授权后果，并要求近期浏览器认证。 |
| FR-CONN-015 | P0 | 锁定客户端清理内存秘密并暂停 Agent，但保留 Keychain 连接；锁定、断开、删除本地数据和浏览器退出使用不同动作与状态。 |
| FR-CONN-016 | P1 | refresh token 具有服务端绝对期限与不活跃期限；密码重置、账号禁用、风险事件和设备撤销使关联 grant 失效。 |
| FR-CONN-017 | P2 | R4 操作只接受 ORYH 服务端签发并在最终写入时验证的短期 step-up assurance；本地生物识别不能替代该保证。 |

### 7.3 模型连接

| ID | 优先级 | 需求 |
|---|---|---|
| FR-MODEL-001 | P0 | 支持至少一种经过验证的 DSH LLM Provider，并明确模型、上下文限制和可用状态。 |
| FR-MODEL-002 | P0 | 用户自带模型密钥时保存到系统凭据库，不写入项目文件、环境文件或 Session。 |
| FR-MODEL-003 | P1 | 支持企业模型网关，使客户端不保存供应商长期密钥。 |
| FR-MODEL-004 | P1 | 管理员策略可以限制可用 Provider、模型、数据地域和推理能力。 |
| FR-MODEL-005 | P1 | 模型不可用时保留用户草稿，展示可恢复错误，不重复业务写操作。 |

### 7.4 会话与对话

| ID | 优先级 | 需求 |
|---|---|---|
| FR-CONV-001 | P0 | 新建、重命名、恢复和归档会话；列表按企业隔离。 |
| FR-CONV-002 | P0 | 会话标题区域持续显示当前企业、用户身份和连接状态。 |
| FR-CONV-003 | P0 | 支持流式回答、取消当前生成、后续消息和明确的工具执行状态。 |

## 8. 非功能需求

### 8.1 安全与隐私

- NFR-SEC-001：生产环境中模型不可获得任何 ORYH 或模型供应商真实凭据。
- NFR-SEC-002：跨租户读取、写入、Skill、缓存和会话混用必须结构上不可发生。
- NFR-SEC-003：高影响工具必须经过不可绕过的本地确认策略。
- NFR-SEC-004：本地持久化业务数据在生产发布前必须具备加密、权限和删除策略。
- NFR-SEC-005：默认不发送会话正文、附件、工具参数和工具结果到遥测服务。
- NFR-SEC-006：客户端只连接显式允许的 ORYH 和模型端点，拒绝任意网络目标。
- NFR-SEC-007：账号认证、设备授权、本地解锁和高风险 step-up 使用不同状态、凭据和审计语义。
- NFR-SEC-008：真实企业发布前，设备凭据交付必须通过短 TTL、并发单次消费、限流、recent auth、CSRF 和 no-store 测试。

完整要求见[安全与隐私](05-security-and-privacy.md)。

### 8.2 可靠性

- NFR-REL-001：读取请求可进行有界重试；未知结果的写请求不得自动重试。
- NFR-REL-002：客户端重启后不会自动执行之前未确认或结果未知的写操作。
- NFR-REL-003：token 刷新并发只允许一个有效轮换过程，其余请求等待结果。
- NFR-REL-004：会话事件、业务工具执行和 ORYH 审计之间保留关联标识。
- NFR-REL-005：Skill 同步失败不得删除最后可用目录。
- NFR-REL-006：refresh 成功以新 credential bundle 原子持久化为完成点；崩溃或保存失败不能留下部分更新。

### 8.3 性能

- NFR-PERF-001：已配置设备上的冷启动目标为 p95 小于 5 秒，恢复到可输入状态。
- NFR-PERF-002：本地 UI 交互响应目标为 p95 小于 100 毫秒。
- NFR-PERF-003：工具调用发出后 1 秒内必须显示进行中状态；外部模型和 API 总耗时单独观测。
- NFR-PERF-004：首页仅拉取有界的个人工作数据，长列表使用分页或增量加载。
- NFR-PERF-005：附件在进入模型前按用途和上限处理，不把二进制内容写入 Session JSON。
- NFR-PERF-006：确定性入口、刷新和只读重跑的模型调用数必须为零，并能在测试中直接断言。
- NFR-PERF-007：业务线程对每种关系边设置查询上限、分页和独立超时；局部失败不能清空已成功来源。

### 8.4 可访问性与本地化

- NFR-A11Y-001：目标符合 WCAG 2.2 AA，所有关键流程可用键盘和屏幕阅读器完成。
- NFR-A11Y-002：颜色不是状态或风险的唯一表达方式。
- NFR-I18N-001：首发支持简体中文和英文；服务端原始状态与用户可读标签分离。
- NFR-I18N-002：日期、时区、金额、币种和数字按租户与用户设置显示，API 仍使用规范值。

### 8.5 可维护性

- NFR-MAIN-001：ORYH OpenAPI 是 API 类型和兼容性测试的来源，不手写重复接口模型。
- NFR-MAIN-002：所有 ORYH 产品能力位于本仓库的外部 DSH 插件或组装层。
- NFR-MAIN-003：锁定 DSH 精确版本，升级作为独立变更并执行完整契约与快照测试。
- NFR-MAIN-004：业务工具、UI 卡片和 Skills 的版本关系可追踪。
- NFR-MAIN-005：ORYH 路由、模型、Skill 和设计事实基线发生变化时生成覆盖差异并重新审查工作空间、业务线程和 Operation。

## 9. 成功指标

### 9.1 激活

- 新用户首次启动至 device flow 完成的成功率。
- 首次连接至看到“我的工作”的中位耗时。
- 连接后七天内至少完成一次有效业务任务的用户比例。

### 9.2 任务效果

- 工时、费用、请假和审批任务的成功完成率。
- 每个流程中用户纠正字段的次数和失败重试次数。
- 从打开待办到写入业务结果的中位时间。
- 高频任务由直接 Operation 完成的比例、每项任务避免的模型调用数和结果刷新耗时。
- 用户从确定性结果选择“询问 AI”的比例，用于判断哪些场景真正需要推理。
- 用户从待办定位到当前状态、当前持有人和阻塞项的成功率与用时。
- 跳转 Console 后完成操作的比例，用于判断哪些流程不适合留在对话中。

### 9.3 安全与质量

- 自动扫描发现的凭据进入模型、Session、日志或遥测事件数量必须为零。
- 已知结果不明的重复写入数量必须为零。
- 跨租户错误工具调用和数据展示数量必须为零。
- 崩溃率、无响应率、令牌刷新失败率和 Skill 同步失败率。

指标必须使用不含业务正文的事件和聚合数据实现；不得为了产品分析放宽隐私要求。

## 10. 发布范围定义

### 10.1 技术验证版

只使用测试租户和测试数据，完成 device flow、系统凭据库、租户绑定会话、`/auth/me`、我的工作、一个服务端草稿写入和一个确认卡片。不作为真实企业使用版本。

### 10.2 MVP

覆盖普通员工与审批人的第一条纵向闭环：能力派生的“我的工作/提交中心/决策中心”、可刷新和固定的业务视图、工时、费用、附件、单项审批、可重建业务线程、evidence packet、会话恢复、Console 深链和中英文。请假、资源预订可在不削弱上述闭环的前提下作为同阶段扩展。已知入口和只读重跑不依赖模型。达到[测试与验收](07-test-and-acceptance.md)中的全部 MVP 门禁。

### 10.3 企业可用版

增加报价到收款、采购到付款、费用报销到付款、工资到发薪、generic objects 等完整业务线程，以及企业模型网关、签名更新、加密本地存储、企业策略、完整诊断和受支持平台矩阵。管理员与批量能力按风险逐步开放。

## 11. 前置依赖

生产实现依赖 ORYH 服务端提供一个**按当前用户权限返回、但不渲染任何凭据的 Skill 内容接口**。当前 personal bundle 会把 access token 写入 Markdown，不符合本客户端的安全要求。该差距和其他后端依赖记录在[技术架构](04-technical-architecture.md#11-oryh-服务端依赖与差距)。

ORYH 产品事实、API/模型/Skill 审计基线和完整客户端定位见[ORYH 产品模型与客户端蓝图](10-oryh-product-model-and-client-blueprint.md)。
